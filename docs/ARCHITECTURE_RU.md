# Архитектура и эксплуатация

## Границы интеграции

Сервис использует документированные методы Flight Data API:

- `GET /aviasales/v3/prices_for_dates` — кэш цен на заданные даты и прямой путь Aviasales;
- `GET /aviasales/v3/grouped_prices` — дневной календарь и прямой путь Aviasales;
- `POST /links/v1/create` — преобразование прямых URL в партнёрские Travelpayouts.
- `POST /search/affiliate/start` и `/search/affiliate/results` — опциональный живой поиск.

Это не live-search и не бронирование. Сервер строго фильтрует результат по маршруту и точным
датам, потому что Data API может вернуть ближайшую дату. Пустой список означает отсутствие
подходящей записи в кэше, но не отсутствие рейсов.

Пустые ответы Data API снабжаются машинным полем `empty_reason` и по умолчанию не
кэшируются (`EMPTY_CACHE_TTL_SECONDS=0`). Это позволяет следующему запросу сразу проверить
обновление upstream-кэша. При необходимости короткое отрицательное кэширование можно включить
ненулевым TTL.

`live_search_flights` не использует Redis-кэш результатов. Он доступен только проектам, которым
Travelpayouts отдельно разрешил Flight Search API (официальное требование — от 50 000 MAU).
MCP-клиент обязан передать реальные данные инициировавшего поиск пользователя в HTTP-заголовках
`X-User-IP`, `User-Agent` и `Referer`; сервер не принимает эти значения от языковой модели.
Поиск может занимать 30–60 секунд. Автоматическое получение booking URL запрещено правилами
провайдера, поэтому инструмент возвращает цены и маршруты без ссылки покупки.

Поле `link` Data API само по себе не является партнёрской ссылкой. Сервер формирует полный
длинный URL Aviasales, отправляет до 10 URL в Partner Links API и принимает результат только
при `code=success`, `status=200`, совпадении `trs` и `marker`, успешном статусе каждой ссылки и
непустом HTTPS `partner_url`. Прямой URL наружу не возвращается. Для календаря преобразуются
пять самых дешёвых дат. Квота ограничена 90 запросами в минуту при официальном максимуме 100.

## Очередь и масштабирование

MCP-процесс валидирует аргументы, проверяет кэш, помещает JSON-задание в Redis Stream и ожидает
отдельный ключ результата. Worker читает consumer group и подтверждает сообщение только после
публикации результата. Зависшие pending-сообщения забирает reclaimer; повторяющиеся внутренние
сбои после лимита попыток попадают в ограниченный dead-letter stream.

Защитные границы:

- `QUEUE_MAX_LENGTH` — максимальная глубина очереди;
- `JOB_TIMEOUT_SECONDS` — дедлайн ожидания и самого задания;
- `WORKER_CONCURRENCY` — параллельные задания в одном контейнере;
- `WORKER_MAX_ATTEMPTS` — число попыток временно неуспешного upstream-вызова;
- `CACHE_TTL_SECONDS` — дедупликация повторных запросов по SHA-256 нормализованных параметров;
- `EMPTY_CACHE_TTL_SECONDS` — короткий TTL пустого ответа; `0` полностью отключает его кэширование;
- `LIVE_SEARCH_TIMEOUT_SECONDS` — отдельный дедлайн долгого живого поиска;
- `LIVE_SEARCH_REQUESTS_PER_HOUR` — распределённая почасовая квота на IP пользователя;
- `RESULT_TTL_SECONDS` — уборка результатов, которые уже некому получить.
- `STREAM_LEASE_SECONDS` — время до reclaim задания аварийного worker'а;
- `PARTNER_LINKS_PER_MINUTE` — распределённая квота Partner Links API;
- `MCP_REQUESTS_PER_MINUTE` — общая защита входного endpoint;
- circuit breaker временно прекращает вызовы при серии отказов Travelpayouts.

Redis нельзя публиковать наружу. Для нескольких хостов используйте управляемый Redis с TLS и
аутентификацией. Масштабирование следует ограничить квотой Travelpayouts: очередь не отменяет
лимиты поставщика.

## Отказоустойчивость

- HTTP 429/5xx, сетевые ошибки и таймауты повторяются worker'ом.
- Ошибки 4xx не повторяются.
- Переполненная очередь возвращает структурированную ошибку `QUEUE_FULL`.
- Общий deadline ограничивает всю цепочку retry, поэтому worker не работает после таймаута.
- Успешный ответ кэшируется только после полной обработки.

Redis Streams обеспечивает повторную доставку неподтверждённого сообщения после lease. Вызовы
upstream имеют семантику at-least-once: при падении после внешнего POST, но до ACK запрос может
повториться. Partner Links API не совершает покупку и безопасен для такого повтора.

## Безопасность

Секреты хранятся только в переменных окружения; `.env` исключён из Git и Docker build context.
MCP требует Bearer-токен, сравниваемый constant-time, scope `flights:read` и привязку к resource.
Transport Security содержит явные Host/Origin allowlist. `/readyz` не раскрывает значения.
Для публичного multi-tenant сервиса статический service token следует заменить внешним OAuth
2.1/JWT verifier; TLS и дополнительный per-client rate limit должны находиться на ingress.

## Наблюдаемость

Логи не содержат параметров токена. Для production рекомендуется собирать:

- глубину `aviasales:jobs`;
- время от постановки до результата и долю таймаутов;
- cache hit ratio;
- коды upstream и число повторов;
- загрузку worker slots и Redis latency.

## Ограничения результата

Data API не возвращает гарантированную live-доступность или тарифные правила. Партнёрская ссылка
ведёт на результаты Aviasales, где цена и наличие проверяются повторно. Для работы `trs` должен
принадлежать проекту, подписанному на программу Aviasales; иначе Partner Links API отклонит URL,
а MCP-сервер не вернёт непартнёрскую замену.
